# Security

Every uploaded file is **untrusted input**, and every conversion engine is treated as code that
may be exploited by its input. The design goal is that a malicious file can at worst fail its
own conversion: it must not reach other users' files, the platform's credentials, the network,
or the host.

This document describes the protections that exist today and where they are implemented.
Limits and their values are in [LIMITS.md](LIMITS.md); data handling is in
[PRIVACY.md](PRIVACY.md).

## Threat model

| Threat | Main defenses |
| --- | --- |
| Malicious file exploits an engine (ImageMagick, LibreOffice, FFmpeg, …) | bubblewrap sandbox or unprivileged engine user, minimal environment, resource limits, per-job directory, restrictive engine configuration |
| Engine reads other jobs' files or the worker's secrets | sandbox exposes only the job directory; environment never inherited; jobs run in private `0700` directories |
| Engine contacts the network (SSRF, exfiltration) | `--unshare-all` network namespace; ImageMagick URL/delegate coders disabled; Pandoc `--sandbox` |
| Command injection | engines are spawned from argument arrays, never a shell; file names never reach the command line (inputs are staged under generated names) |
| Path traversal (file names, archive entries) | storage keys are generated by the platform; archive listings are checked before extraction; extracted trees are walked again |
| Zip/archive bombs | entry count, extracted size and compression-ratio limits checked from the listing *and* enforced by `fsize` while extracting |
| Decompression/pixel bombs | ImageMagick `area`/`width`/`height` limits; output pixel validation; media duration and page limits |
| Resource exhaustion | per-process CPU time, address space, file size and open-file limits; whole-job deadline; process-group kill; worker concurrency; rate limiting |
| Format confusion (a `.png` that is really HTML/SVG/PDF) | content-based detection before upload, on upload completion and again in the worker; mismatches fail with `format-mismatch` |
| Output used to attack the site (e.g. converted HTML) | downloads are attachments with `nosniff` and a `sandbox` CSP; outputs are validated by content |
| Stealing someone's job or files | 256-bit job tokens (only a SHA-256 hash is stored), timing-safe comparison, short-lived signed URLs, random IDs |
| Spreadsheet formula injection | CSV imported by LibreOffice with formula evaluation disabled |
| Abuse and cost attacks | rate limits per anonymous client, size limits checked before upload, workers required for job creation |

## Engine isolation

All server engines run through `ProcessRunner` (`packages/engines/src/runner.ts`).

**Always applied**

- Commands are spawned from argument arrays — never through a shell.
- A minimal environment: `PATH`, `HOME`, `TMPDIR`, `LANG`, `LC_ALL` and engine-specific
  variables only. Database URLs, storage keys and signing secrets are never visible to engines.
- Each process runs in its own process group and the whole group is killed (`SIGKILL`) on
  timeout, cancellation, or when the main process exits (no orphaned helpers).
- `prlimit` (when installed — the worker image includes it): CPU seconds derived from the job
  deadline, address space (`VANILLATE_ENGINE_MEMORY_MB`, default 4 GiB per process), largest
  writable file, and 1024 open files.
- Only the tail of stderr is kept (16 KiB) and stdout is capped, for logs only. Engine output
  is never shown to users (see [Error handling](#error-handling)).

**bubblewrap sandbox** (`VANILLATE_SANDBOX=auto|bwrap|none`, default `auto`)

```
bwrap --die-with-parent --new-session --unshare-all --cap-drop ALL
      --ro-bind /usr /usr  --ro-bind-try /opt /opt  --proc /proc --dev /dev --tmpfs /tmp
      --ro-bind-try /etc/<allowlisted entries>   (fonts, ld.so, passwd, engine configs …)
      --bind <job directory> <job directory>  --chdir <job directory>
```

- New user, PID, IPC, UTS, cgroup and **network** namespaces: no network access at all.
- The root filesystem is empty except for read-only `/usr` (and `/opt`), a private `/tmp`, and
  an allowlist of `/etc` entries engines need. No other job's directory, no application code or
  configuration, no credentials.
- The job directory is the only writable path.

**Unprivileged engine user** (`VANILLATE_ENGINE_USER=auto|none|<uid>:<gid>`)

When the worker runs as root, engines run as `nobody` (65534) by default. They then cannot read
the worker's environment through `/proc`, its files, or other jobs' directories (each job
directory is `0700` and owned by the engine user only while that job runs).

**Isolation is required in production.** The worker refuses to start with `NODE_ENV=production`
unless at least one of the two isolation layers is active (`workers/runtime/src/main.ts`).
`VANILLATE_ALLOW_UNISOLATED=1` overrides this and is unsafe. The recommended production setup
uses **both**: bubblewrap for namespaces and the engine user as a second layer.

> bubblewrap needs unprivileged user namespaces. In Docker this usually means a seccomp/AppArmor
> profile that permits `unshare`/`clone` with new namespaces. If that is not possible, run the
> worker as root with the engine user, and keep the worker container on a network with no
> access to internal services.

### Engine-specific hardening

| Engine | Hardening (`packages/engines/src/engines/*.ts`) |
| --- | --- |
| ImageMagick | A restrictive policy is written into every job (`POLICY_XML`): memory/map/disk/area/width/height/time/thread limits, **all delegates disabled**, script and network coders (`MVG`, `MSL`, `URL`, `HTTP(S)`, `FTP`, `TEXT`, `LABEL`, …) disabled, PostScript/PDF/SVG coders disabled (those formats go to dedicated engines), `@file` indirection disabled. Worker images install the identical file (`packages/engines/config/imagemagick/policy.xml`) as the system policy. |
| LibreOffice | An isolated user profile per job; the import filter is **forced per format** (`--infilter`) so a file is never auto-detected as something more dangerous; CSV formula evaluation is disabled. |
| Pandoc | Runs with `--sandbox` when the build supports it; otherwise only when engine processes are isolated (refused otherwise). |
| 7-Zip | The listing is checked before extraction (encrypted entries, links and special files, absolute or `..` paths, path length, entry count, total size, compression ratio); extraction is size-limited and the extracted tree is walked again. |
| Ghostscript | `-dSAFER`. |
| FFmpeg | Inputs are probed first (streams, duration) and checked against media limits; only local files are used. |
| ExifTool | Metadata output is filtered to public, non-sensitive tags. |

## Input validation

1. **Before upload (browser).** The converter detects the format from the file's bytes and
   refuses files that do not match the page (`apps/web/src/components/converter/`). Size limits
   are checked before anything is sent.
2. **Job creation (API).** Strict request schemas (`zod`, unknown fields rejected), a 64 KiB
   body limit, the declared format must be accepted by the route, size and file-count limits
   per mode and category, options validated against the route's option definitions, and rate
   limits (`packages/jobs/src/service.ts`).
3. **Upload.** Signed upload requests are bound to one storage key, method, content type and
   **exact size**; the local driver streams to a temporary file and rejects anything longer or
   shorter (`packages/storage/src/local.ts`).
4. **Upload completion.** The stored size is re-checked and the format is detected from the
   stored bytes (head, tail, and inflated ZIP head for container formats). A mismatch deletes the
   input and fails the job (`format-mismatch`).
5. **Worker.** Inputs are downloaded with exact-size checks and detected again — nothing that
   crossed the storage boundary is trusted (`workers/runtime/src/process.ts`).
6. **Outputs.** Every output is detected by content and must match the expected format, be
   non-empty, within size limits and within pixel limits (`workers/runtime/src/outputs.ts`).
   Output names are generated from sanitized input names.

## Web application

- **Headers** (`apps/web/next.config.ts`): Content-Security-Policy (`default-src 'self'`,
  `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`,
  `connect-src` limited to the site and the configured storage origin), HSTS, `nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, and a restrictive
  `Permissions-Policy`. Pages are statically generated, so the CSP cannot use nonces and allows
  inline scripts; there is no user-controlled HTML anywhere on the site.
- **JSON-LD** is serialized with `<` escaped, so data can never close the script element.
- **Browser processing** runs in a dedicated Web Worker; files stay in memory and are handed
  back as `blob:` URLs.
- **API responses** are `Cache-Control: no-store`. Internal error details are logged, never
  returned.

## Access control

- No accounts. A job is accessed with a random **job token** (256 bits) returned once at
  creation. Only its SHA-256 hash is stored; comparisons are timing-safe. Wrong or missing
  tokens get `403 unauthorized`; malformed IDs are rejected before any lookup.
- Job and input IDs are random (`job_` + 26 base32 characters).
- Uploads and downloads use **signed requests** that expire (`retention.signedUrlSeconds`,
  15 minutes): HMAC-SHA-256 tokens for local storage, presigned URLs for S3. Download links are
  only issued for completed, unexpired jobs.
- Downloads are served as attachments with `X-Content-Type-Options: nosniff` and
  `Content-Security-Policy: default-src 'none'; sandbox`, so converted HTML or SVG is never
  rendered as part of the site.

## Abuse prevention

- Rate limits per anonymous client key: 10 jobs per minute and 100 per hour
  (`catalog/limits.json`). The key is a salted SHA-256 of the client IP (`RATE_LIMIT_SALT`);
  IPs are not stored.
- Jobs are refused (`server-unavailable`) when no live worker can run them, instead of queuing
  work nobody will do.
- Size limits are checked before upload, so oversized files never reach storage.
- Worker concurrency, per-job deadlines and pools bound the work any client can cause.

## Error handling

Errors are typed (`packages/core/src/errors/codes.ts`) with a kind — `user`, `developer`,
`engine`, `infrastructure`, `system` — an HTTP status and localized messages. Users receive the
code and a localized, actionable message only. Engine stderr, stack traces and file paths go to
structured logs. Unknown errors become `internal-error`.

## Secrets

| Secret | Used by |
| --- | --- |
| `DATABASE_URL` | web app, worker |
| `STORAGE_SIGNING_SECRET` (≥ 32 characters) | web app, worker (local storage) |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | web app, worker (S3 storage) |
| `RATE_LIMIT_SALT` | web app |

Secrets are read from the environment, never committed (`.env*` is ignored except
`.env.example`), never passed to engines, and never logged.

## Reporting a vulnerability

Please report security issues privately to the maintainers (Vanillate Studio) rather than in a
public issue. Include the affected component, a reproduction file if possible, and the impact.

## Known gaps

- The CSP allows `'unsafe-inline'` scripts because pages are static (no per-request nonces).
- Per-job cgroups are not used; give each worker container a memory and CPU limit as well.
- There is no malware scanning of uploads; files are converted in isolation, not inspected for
  malware.
- Rate limiting is per IP-derived key only; a CAPTCHA or proof-of-work for heavy jobs is not
  implemented.
