# Storage

Server jobs keep their input and output files in object storage (`packages/storage`). Storage
is temporary by design: every object belongs to a job and is deleted by the job lifecycle
([QUEUE.md](QUEUE.md#expiry-and-cleanup)). Job records hold only keys and metadata.

## Interface

`Storage` (`packages/storage/src/types.ts`):

| Method | Used by |
| --- | --- |
| `createUploadUrl(key, { contentType, size, expiresIn })` | API: signed upload request for the browser |
| `createDownloadUrl(key, { filename, contentType, expiresIn })` | API: signed download link for a completed job |
| `head(key)` / `readRange(key, start, end)` | API: verify size and detect the format of an uploaded input |
| `read(key)` / `write(key, body, { contentType, size })` | worker: download inputs, upload outputs; local upload route |
| `delete(key)` / `deleteMany(keys)` | job service: cancellation, failure, completion, retention |

### Keys

```
jobs/<jobId>/in/<inputId>
jobs/<jobId>/out/<outputId>
```

Keys are generated by the platform from random IDs and validated by `assertValidKey` on every
call; user-supplied names never become paths. File names only appear in the
`Content-Disposition` of downloads (sanitized, RFC 6266 encoded).

## Drivers

Selected with `STORAGE_DRIVER` (`packages/storage/src/config.ts`).

### `s3` — production

Any S3-compatible service (AWS S3, Cloudflare R2, MinIO, …) through presigned URLs
(`aws4fetch`, SigV4). Browsers upload and download **directly**; file bytes never pass through
Vercel functions.

- Upload URLs sign `content-type` and `content-length`, so storage rejects uploads of a
  different size or type.
- Download URLs set `response-content-disposition` to an attachment with the output's name.
- The API reads only the first and last 64 KiB of an upload to verify it.

| Variable | Default | |
| --- | --- | --- |
| `S3_ENDPOINT` | — | Required, e.g. `https://<account>.r2.cloudflarestorage.com` |
| `S3_PUBLIC_ENDPOINT` | `S3_ENDPOINT` | Endpoint browsers use, if different (also added to the CSP `connect-src`) |
| `S3_REGION` | `auto` | |
| `S3_BUCKET` | — | Required |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | — | Required; least-privilege key for this bucket |
| `S3_FORCE_PATH_STYLE` | `true` | `false` for virtual-hosted-style URLs |

Bucket setup:

1. **Private** bucket (no public read).
2. **CORS** allowing the site origin to `PUT` (headers `content-type`) and `GET`.
3. A **lifecycle rule** deleting objects under `jobs/` older than one day — a backstop in case
   workers (which run the retention sweeper) are down for a long time.

### `local` — development and single-machine self-hosting

Files live under `STORAGE_LOCAL_DIR`; transfers go through the web app's
`/api/v1/storage/{token}` route with **HMAC-SHA-256 signed tokens**
(`packages/storage/src/signing.ts`) that bind the key, method, expiry, content type, size and
download file name.

- Uploads stream to a temporary file and are renamed into place only when exactly the signed
  size arrived; longer bodies fail with `bad-request`, shorter ones with `upload-incomplete`.
- Paths are resolved under the root and refused if they escape it.
- Downloads are attachments with `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, no-store`.
- Not suitable for Vercel (no shared persistent disk). The web app and the worker must share
  the directory (a volume).

| Variable | Default | |
| --- | --- | --- |
| `STORAGE_LOCAL_DIR` | — | Required |
| `STORAGE_SIGNING_SECRET` | — | Required, ≥ 32 characters |
| `STORAGE_PUBLIC_PATH` | `/api/v1/storage` | Path or absolute URL of the transfer route |

### `memory` — tests

In-process objects with the same size checks; the standalone worker refuses it.

## Lifetimes

From `catalog/limits.json` → `retention` ([LIMITS.md](LIMITS.md#retention)):

| | |
| --- | --- |
| Signed upload/download requests | 15 minutes (`signedUrlSeconds`; download links never outlive the job's outputs) |
| Inputs | Deleted when the job completes, fails or is cancelled; unstarted uploads after 60 minutes |
| Outputs | 60 minutes after completion (`outputSeconds`) |

## File lifecycle

```
createJob ── signed PUT ──▶ jobs/<job>/in/<input>
                              │ completeUpload: size + content detection (mismatch → deleted)
                              ▼
worker: read → sandbox → validate → write jobs/<job>/out/<output>
                              │ complete: inputs deleted
                              ▼
browser: signed GET (attachment) … retention sweep deletes outputs
```

Deletion failures never fail a request; they are logged (`storage.cleanup_failed`) and the
sweeper retries when the job expires.
